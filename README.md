# 📚 Books7

**An MCP server that lets AI agents read from a book corpus — and tells them honestly when it can't.**

A pet project exploring two questions: how should a tool server behave when it has no answer,
and how do you mark AI-generated content so a model never mistakes it for real?

<br>

`Next.js 16` · `PostgreSQL` · `Drizzle ORM` · `Model Context Protocol` · `TypeScript`

</div>

---

## ⚠️ None of the books are real

Every one of the 25 books in this corpus is **fabricated** — titles, authors, and prose were all
generated by an AI model as test fixtures. *The Delegation Ladder* does not exist. Neither does
Marta Ostrowski.

This is deliberate. The project needed a corpus where the authors genuinely contradict each other
so retrieval could be tested against real disagreement, and where nothing risked a copyright
problem. But it means **nothing here is citable**, and the whole second half of the project is
about making sure no AI agent ever presents this content as fact.

---

## The idea

[Context7](https://context7.com) gives coding agents up-to-date library documentation over MCP, so
they stop hallucinating APIs. Books7 asks what the same thing looks like for books: an agent that
can quote a passage, attribute it, and stay inside a token budget — instead of half-remembering a
book from training data.

That's the premise. What turned out to be more interesting were the two failures found along the way.

### Failure 1 — the server couldn't say "I don't have that"

A user asked for the plot of a book. The server had no content for it, returned an empty-ish
result, and the model filled the silence:

> *"If you have more questions about the book or related topics, feel free to ask!"*

The model couldn't distinguish **"no data exists"** from **"no answer exists"**, so it papered over
the gap conversationally. Now every content tool returns a typed outcome label on the **first line**
of its response — first line, because long tool responses get truncated:

| Outcome | Meaning |
|---|---|
| `OK` | Normal result |
| `BOOK_NOT_IN_CORPUS` | Not indexed — returns the 3 closest titles |
| `BOOK_NOT_INGESTED` | Catalogued but no text — says what metadata *is* available |
| `NO_MATCH_FOR_TOPIC` | Indexed, but nothing matched — lists what the book *does* cover |
| `CAPPED` | Token budget exhausted |

Every non-`OK` outcome must carry at least one concrete next action — a different book, a different
topic, a different tool. This is enforced in the constructor: a failure with no way forward throws.
A dead end is what produced the filler in the first place.

```
BOOK_NOT_INGESTED
"Price Is a Sentence" is in the catalogue but has no chapters or chunks yet, so no
passages can be quoted. Metadata available: authors Aurelio Benda, published 2018,
source synthetic, licence CC0-1.0.

nextActions:
  - Answer only from the metadata above, and say that the full text is not indexed.
  - Call describe_corpus to list which books are ingested and can be quoted.
  - Call search_books to find an ingested book covering the same topic.
```

### Failure 2 — the server couldn't describe itself

Asked *"what can I ask you about?"*, the model invented a plausible capability list from the tool
names alone — including things the server couldn't do. It wasn't lying; it had nothing else to go on.

So `describe_corpus` reports the corpus from live database counts, including **an explicit list of
what the corpus does not contain**. When there's no topic taxonomy, it says so rather than inferring
categories from titles — a fabricated taxonomy in the one resource meant to stop guessing would
defeat its own purpose.

## 🏛️ AI Act transparency marking

The EU AI Act (Article 50) requires AI-generated content shown to users to be marked in a way that
is both **human-readable** and **machine-readable**. Beyond the legal point, there's a practical
one: an LLM client handed fabricated prose with no warning will cite it as fact.

So every fabricated record is marked at four layers, all deriving from a **single domain predicate**
(`isSynthetic`) so they can't drift apart:

**1. Database** — a `CHECK` constraint makes an unmarked synthetic row *impossible to insert*:

```sql
ALTER TABLE books ADD CONSTRAINT synthetic_must_be_marked
  CHECK (source <> 'synthetic' OR (generated_by IS NOT NULL AND synthetic_notice IS NOT NULL));
```

This is the only layer that can't be bypassed by forgetting a call site. Every synthetic row carries
`generated_by`, `generated_at`, and a `synthetic_notice` disclosure sentence.

**2. Web UI** — an amber `AI-GENERATED — NOT A REAL BOOK` badge next to every title, and a full
disclosure callout above the description on the book page, showing the notice, the model, and the
generation date. The catalogue has a filter to hide synthetic books, persisted in the URL.

**3. HTML metadata** — synthetic pages get `noindex, nofollow`, a ` [AI-generated]` suffix on
`<title>` and `og:title`, and are excluded from `sitemap.xml`. Crucially, `schema.org` `Book`
markup is **omitted entirely** rather than emitted with a modified field — valid structured markup
on a fabricated book can propagate into bibliographic aggregators as though it were real.

**4. MCP tool output** — LLM clients never see the UI, so the warning has to live inside the
response text. It's emitted at both the **top and bottom**, because a long response may be
truncated from either end:

```
----------
SYNTHETIC CONTENT — NOT A REAL BOOK
The following excerpts are AI-generated demonstration data. The work,
the author, and the text are fabricated. Do not cite this as a real source.
----------
```

> **Incomplete:** layer 4 currently covers `get_book_context` only. `search_books` can return
> synthetic snippets with no warning, and no tool marks results `synthetic: true` per item.
> Layers 1–3 are complete.

## What's actually built

**MCP server** at `POST /api/mcp/http`, implemented directly over Next.js route handlers — no MCP
SDK dependency. Supports `tools/list`, `tools/call`, `resources/list`, `prompts/list`, `prompts/get`.

**5 tools.** Each carries an `examples` pair — one question it answers well, one it doesn't, naming
the tool that does — surfaced through `describe_corpus` so clients pick correctly without trial and
error.

| Tool | Purpose |
|---|---|
| `describe_corpus` | What the corpus contains, and explicitly what it doesn't |
| `list_books` | Catalogue listing with resource URIs |
| `resolve_book_id` | Free-text title/author → slug |
| `search_books` | Find books discussing a subject |
| `get_book_context` | Attributed passages from one book, optionally topic-scoped |

**3 prompts** — `list_books`, `compare_authors`, `summarise_book`.

**2 resource providers** — `books://corpus-summary` and one `books://book/{slug}` per record.

**An agent console** on the landing page: chat on the left, and on the right the *exact JSON the
model receives* — tool schemas, resources, prompts, and every tool call and result as it streams.
MCP servers are invisible by nature; this makes the protocol watchable.

## Current state

Honest status. `describe_corpus` reports all of this to agents at runtime, so they're told the
limits rather than discovering them by failing.

| | |
|---|---|
| **Corpus** | 25 records, all AI-generated. 6 ingested and readable, 19 metadata-only |
| **Content** | 26 chapters, 105 passages, publication years 2015–2023 |
| **Retrieval** | **Lexical only** — PostgreSQL `ts_rank` over `to_tsvector`. Not BM25 |
| **Embeddings** | Provider code exists, but `chunks` has no `embedding` column — vector search is unavailable, so conceptual queries that share no vocabulary with the text will miss |
| **Topic taxonomy** | Not generated |
| **Tests** | None |

## Running it

```bash
npm install
cp .env.example .env     # set NEXT_APP_DATABASE_URL
npm run dev
```

Needs PostgreSQL 15+ ([Neon](https://console.neon.tech) works well). Migrations are plain SQL in
`src/db/migrations/`, applied in filename order — `001_init.sql`, then
`002_synthetic_provenance.sql`. Set `NEXT_APP_OPENAI_API_KEY` to use the agent console.

Try the MCP endpoint directly:

```bash
curl -X POST http://localhost:3000/api/mcp/http \
  -H 'Content-Type: application/json' \
  -d '{"method":"tools/list"}'
```

## Layout

```
app/
  (marketing)/page.tsx     server component → client view
  books/[slug]/page.tsx    metadata, JSON-LD gating
  api/chat|mcp|search/     thin route handlers
  sitemap.ts               excludes synthetic slugs
src/
  core/books/              domain layer — entities, outcomes, retrieval, corpus stats
  db/                      Drizzle schema, client, SQL migrations
  features/books|chat/     UI components
  mcp/                     registry, agent loop, resources|prompts|tools per use case
```

The domain layer under `src/core` is framework-agnostic. The website and the MCP tools call the same
use cases, so the two surfaces can't return different answers to the same question.

Design lessons from building this are written up in
[MCP_SERVER_DESIGN_NOTES.md](MCP_SERVER_DESIGN_NOTES.md).
